# ✦ ResearchAI

**ResearchAI** is a Multi-Agent AI research assistant built with **Python, LangChain, Ollama, Qwen3, and Streamlit**.

The application takes a research topic and processes it through specialized AI components:

```text
User
  │
  ▼
Research Topic
  │
  ▼
🔎 Search Agent
  │
  ▼
📖 Reader Agent
  │
  ▼
✍️ Writer
  │
  ▼
🧐 Critic
  │
  ▼
📝 Final Research Report
```

The project is organized into separate **Agents, Tools, and Pipelines** to keep the code modular and easier to maintain.

# 📂 Folder Responsibilities

The project is divided into three main modules:

```text
src/
│
├── agents/
├── pipelines/
└── tools/
```

Each folder has a specific responsibility.

---

## 🤖 `src/agents/`

This folder contains the AI Agents and AI Chains.

```text
src/
└── agents/
    ├── __init__.py
    └── agents.py
```

The `agents.py` module contains components such as:

```text
Search Agent
Reader Agent
Writer Chain
Critic Chain
```

### Search Agent

The Search Agent uses a web search tool to find information related to the user's topic.

Responsibilities:

- Search the web
- Find relevant information
- Prefer reliable sources
- Prefer accessible sources
- Return useful source URLs
- Avoid inventing information

Conceptually:

```text
Topic
  ↓
Search Agent
  ↓
Web Search Tool
  ↓
Search Results
```

---

### Reader Agent

The Reader Agent analyzes search results and reads relevant web pages using the scraping tool.

Conceptually:

```text
Search Results
      ↓
Reader Agent
      ↓
scrape_url
      ↓
Scraped Content
```

Responsibilities:

- Identify a relevant source
- Scrape the web page
- Extract useful information
- Focus on information related to the topic
- Avoid inventing information when scraping fails

---

### Writer Chain

The Writer is implemented as a **Chain**.

It receives:

```text
Research Topic
      +
Search Results
      +
Scraped Content
```

and generates a structured research report.

Conceptually:

```text
Research
   ↓
Prompt
   ↓
Qwen3
   ↓
Research Report
```

The report is structured around:

```text
Introduction
Key Findings
Conclusion
Sources
```

---

### Critic Chain

The Critic is implemented as a **Chain**.

It receives the generated report and evaluates it.

The current output contains:

```text
Score

Strengths

Areas to Improve

One line verdict
```

The Critic currently provides feedback after the Writer finishes.

The feedback is displayed to the user but is not yet automatically sent back to the Writer.

# 🧠 `research_manager.py`

`research_manager.py` manages the research execution and persistent caching.

It provides functions such as:

```python
run_search()
run_reader()
run_writer()
run_critic()
run_research_pipeline()
```

The complete workflow is connected through a shared `state`:

```python
state["search_results"] = run_search(topic)

state["scraped_content"] = run_reader(
    topic,
    state["search_results"]
)

state["report"] = run_writer(
    topic,
    state["search_results"],
    state["scraped_content"]
)

state["feedback"] = run_critic(
    topic,
    state["report"]
)
```

The manager also prevents unnecessary repeated execution by loading previously saved results when available.

# 💾 Persistent Research Cache

Research results are stored inside:

```text
research_data/
```

A topic is converted into a unique hash, creating a separate directory for its results.

Example:

```text
research_data/
│
├── 7a4c.../
│   ├── search.txt
│   ├── scraped.txt
│   ├── report.txt
│   └── feedback.txt
│
└── b81f.../
    ├── search.txt
    ├── scraped.txt
    ├── report.txt
    └── feedback.txt
```

### First execution

```text
Search Agent  → Run → Save
Reader Agent  → Run → Save
Writer        → Run → Save
Critic        → Run → Save
```

### Repeated execution

```text
Search Agent  → Cache ✅
Reader Agent  → Cache ✅
Writer        → Cache ✅
Critic        → Cache ✅
```

This is especially useful when using a local LLM because inference can take considerable time.

# 🤖 Local LLM

The project uses:

```text
Qwen3:4b
```

through **Ollama**.

Architecture:

```text
Streamlit
    ↓
research_manager
    ↓
Pipeline
    ↓
Agents / Chains
    ↓
ChatOllama
    ↓
Ollama
    ↓
Qwen3:4b
```

The language model runs locally.

This means the main LLM inference does not require a cloud LLM API.

### Local approach

```text
Application
     ↓
LangChain
     ↓
Ollama
     ↓
Qwen3:4b
```

### API approach

The project could theoretically be adapted to use a cloud LLM API instead:

```text
Application
     ↓
LangChain
     ↓
Cloud LLM API
     ↓
Model Provider
```

The current implementation uses the **local approach** with Ollama.

# 🧩 Agent vs Chain

One of the main learning goals of this project is understanding the difference between Agents and Chains.

## Agent

An Agent can use tools to accomplish a task.

```text
Agent
 ├── Tool 1
 ├── Tool 2
 └── Tool 3
```

Used for:

```text
Search Agent
Reader Agent
```

---

## Chain

A Chain follows a predefined workflow.

```text
Input
 ↓
Prompt
 ↓
LLM
 ↓
Output
```

Used for:

```text
Writer Chain
Critic Chain
```

# 🔗 LangChain

LangChain is used as the main framework for connecting:

- LLMs
- Agents
- Tools
- Prompts
- Chains
- Web research
- Application logic

The project also builds on the concepts of **LangChain Expression Language (LCEL)** for composing components.

Example:

```python
chain = prompt | llm | output_parser
```

The `|` operator passes the output of one component into the next component.

# ⚠️ Current Limitations

### Local inference speed

Qwen3 runs locally through Ollama, so response speed depends on the computer's hardware.

### Web scraping

Some websites may block automated requests or return errors such as:

```text
403 Forbidden
404 Not Found
```

The Reader Agent therefore cannot guarantee that every URL can be scraped.

### Sequential workflow

The current workflow executes one stage after another:

```text
Search
  ↓
Reader
  ↓
Writer
  ↓
Critic
```

There is currently no automatic Writer → Critic → Writer improvement loop.

### Cache invalidation

Cached results can become outdated if prompts, tools, or pipeline logic change. A future version should support explicit cache invalidation or per-stage reruns.
